## 1. Goal

Rewrite the simulator as five direct DataFrame-producing components plus one
short pipeline. Migrate one component at a time, validate its behavioral
contract, and then delete the implementation it replaces.

Every component must document all public and private methods. Add concise code
comments around statistical transformations, parameterizations, or accounting
logic that is not immediately clear from names; avoid narrating obvious code.

Preserve:

- statistical formulas and intended distributions;
- deterministic same-seed behavior;
- calibration and coefficient-recovery quality;
- room, apartment, cohort, and building accounting identities; and
- a clear final building-level DataFrame.

Deliberately retire:

- the stage registry and abstract stage hierarchy;
- the mutable generic state container;
- runtime schema and metadata registries;
- design-builder classes;
- runtime validation-report classes; and
- compatibility adapters for the old public API.

Exact seed-42 hashes and old random draw order are not permanent contracts.

## 2. Target API

```python
NeighborhoodSimulator(config).generate(n_neighborhoods, rng=None)
BuildingSimulator(config).generate(neighborhoods, rng=None)
ApartmentSimulator(config).generate(buildings, rng=None)
ApartmentSimulator.with_context(apartments, buildings, neighborhoods)
ApartmentSimulator.to_cohort_long(apartments)
TotalChildrenSimulator(config, rng=None).generate(apartment_context)
CohortCompositionSimulator(config, rng=None).generate(apartments_with_context)

simulator = StudentPopulationSimulator(config)
final_df = simulator.run()
details = simulator.run_details()
```

Every generation method returns a `pandas.DataFrame`. `run()` returns the final
building-level DataFrame. `run_details()` exists only for research workflows
that need intermediate apartment data.

## 3. Final DataFrame Contract

One row per `building_id`, with columns equivalent to:

- `building_id`, `neighborhood_id`;
- `ses`, `avg_household_size`, `median_age`, `n_daycares_500m`,
  `school_status`;
- `3_rooms`, `4_rooms`, `5_rooms`, `6_rooms`;
- `n_apartments`;
- `n_kindergarten`, `n_elementary`, `n_highschool`; and
- `n_children_total`.

All joins must specify `on=`, `how=`, and `validate=`. The implementation must
not rely on pandas choosing implicit merge keys.

## 4. Model Assignment Guide

The recommendations below assume:

- **Codex** is the implementation-focused option for bounded code edits, tests,
  mechanical migration, and deletion work.
- **GPT-5.6 Sol** is the balanced option for multi-file integration,
  configuration/API design, notebooks, and documentation.
- **GPT-5.6 Terra** is the strongest reasoning/review option for statistical
  semantics, architecture decisions, difficult debugging, and final audits.

If your model picker describes these variants differently, follow the role
rather than the label. For every destructive migration step, use one model to
implement and a different model to review the focused diff and validation
output.

| Step | Primary model | Review model | Reason |
|---|---|---|---|
| 1. Behavioral baseline | GPT-5.6 Terra | Codex | Requires deciding which statistical contracts matter and which old architecture contracts should be discarded. |
| 2. Configuration | GPT-5.6 Sol | GPT-5.6 Terra | Cross-file API/TOML design benefits from balanced integration, followed by semantic review. |
| 3. RNG convention | Codex | GPT-5.6 Terra | Small implementation change, but draw ownership and reproducibility need careful review. |
| 4. Neighborhood component | Codex | GPT-5.6 Sol | Bounded class migration with straightforward distribution and DataFrame tests. |
| 5. Building component | GPT-5.6 Sol | GPT-5.6 Terra | Room-mix generation, overrides, and accounting interact across multiple outputs. |
| 6. Apartment component | Codex | GPT-5.6 Sol | Mostly explicit expansion, joins, reshaping, and focused tests. |
| 7. Total-children model | GPT-5.6 Terra | Codex | NB2 parameterization, feature semantics, and random effects are statistically sensitive. |
| 8. Cohort composition | GPT-5.6 Terra | Codex | Multinomial probabilities and lifecycle effects require statistical care. |
| 9. Building aggregation | Codex | GPT-5.6 Sol | Explicit groupby/merge work with crisp accounting checks. |
| 10. Pipeline replacement | GPT-5.6 Sol | GPT-5.6 Terra | Cross-component integration and deletion boundary require broad context. |
| 11. Validation/API cleanup | Codex | GPT-5.6 Sol | Primarily deletion, import cleanup, and focused replacement tests. |
| 12. Notebook/docs | GPT-5.6 Sol | Codex | Narrative, notebook flow, and API usage need coherent cross-file updates. |
| 13. Final cleanup gate | GPT-5.6 Terra | Codex | Independent architecture/statistical audit, followed by mechanical cleanup. |

For the whole migration, the recommended pattern is:

1. Terra defines or reviews the behavioral contract.
2. Codex implements bounded components and tests.
3. Sol integrates components, notebook, and docs.
4. Terra performs the final statistical and architectural audit.

## 5. Migration Steps

### Step 1: Freeze Behavioral Contracts

1. Add temporary characterization tests for formulas and final outputs without
   testing old architecture details.
2. Record final columns, dtypes, unique/non-null keys, supported room
   categories, and aggregation identities.
3. Record same-seed equality, different-seed variation, seed-42 calibration
   ranges, and coefficient-recovery expectations.
4. Treat exact old hashes as diagnostics only.

**Validation gate**

Run characterization, calibration, and recovery tests against the current
implementation. Do not change production code in this step.

**Deletion:** none.

### Step 2: Simplify Configuration

1. Replace the nine-dataclass hierarchy with a compact loader returning
   component mappings for `simulation`, `neighborhood`, `building`,
   `apartment`, `total_children`, and `cohort`.
2. Fold room-mix settings under `building.room_mix`.
3. Keep a small shared `features` mapping only for references and scales used
   by both outcome models.
4. Make each component validate only its own keys, ranges, and probabilities.
5. Add TOML comments for units and intuition, especially log-scale
   coefficients, median-age effects, NB2 dispersion, random-effect standard
   deviations, lifecycle slopes, and Dirichlet concentration.
6. Remove runtime-only validation and export config sections. Calibration
   thresholds belong in tests; export destinations belong to callers.

**Validation gate**

Focused tests cover valid loading, missing/unknown keys, probability sums,
invalid ranges, TOML comments, and deterministic seed access.

**Deletion after gate:** old config dataclasses and parser branches that have no
remaining consumers.

### Step 3: Introduce One RNG Convention

1. Keep `simulation.seed` as the single configured seed source.
2. Every component accepts `rng: np.random.Generator | None`.
3. `rng=None` creates `np.random.default_rng(config["simulation"]["seed"])`.
4. The pipeline creates one generator from `simulation.seed` and passes that
   same generator through all components.
5. Document the distinction between reproducible isolated component calls and
   reproducible full pipeline runs.

**Validation gate**

For every migrated component, verify equal results for two `rng=None` calls,
equal explicit seeds, and different stochastic values for another seed.

**Deletion:** duplicate RNG initialization code as each component migrates.

### Step 4: Replace Neighborhood Stage

1. Create `neighborhood.py` with `NeighborhoodSimulator`.
2. Move neighborhood generation into `generate()` plus small private helpers.
3. Return only the public neighborhood DataFrame.
4. Do not generate total-count random effects here; those effects belong to
   the model that consumes them.
5. Port behavioral tests to `test_neighborhood.py`.

**Validation gate**

Check row count, columns, unique IDs, configured bounds, school categories,
reproducibility, and absence of latent columns.

**Delete after gate**

- `stages/neighborhoods.py`
- architecture-specific neighborhood-stage tests

### Step 5: Replace Building Stage

1. Create `building.py` with `BuildingSimulator`.
2. Generate building IDs, neighborhood foreign keys, apartment totals, and
   room composition in one component.
3. Return one row per building with `3_rooms` through `6_rooms` and
   `n_apartments`.
4. Keep room-probability, Dirichlet, and multinomial logic private.
5. Preserve configured overrides.

**Validation gate**

Check unique IDs, neighborhood foreign keys, apartment bounds, nonnegative
integer room counts, room sums equal to `n_apartments`, overrides, and
reproducibility.

**Delete after gate**

- `stages/buildings.py`
- old long-form room-composition runtime path
- corresponding stage tests

The compact runtime no longer needs a separate
`building_room_composition` table.

### Step 6: Replace Apartment Stage And Expose Transformations

1. Create `apartment.py` with `ApartmentSimulator`.
2. `generate(buildings)` expands room-count columns into apartment rows.
3. Add `with_context()` for apartment -> building -> neighborhood joins using
   explicit keys and `validate="many_to_one"`.
4. Add `to_cohort_long()` for wide-to-long cohort analysis.
5. Keep transformations visible as named methods.

**Validation gate**

Check expansion row counts, exact room-count recovery, foreign keys, unique
apartment IDs, context columns, join-cardinality failures, and long-view cohort
totals.

**Delete after gate**

- `stages/apartments.py`
- replaced apartment-context code in `design.py`

### Step 7: Replace Total-Children Stage

1. Create `outcomes.py` with `TotalChildrenSimulator`.
2. Put readable feature construction near the expected-count formula.
3. Keep only genuinely shared features in `features.py`; keep NB2 sampling
   private to this component.
4. Generate building and neighborhood random intercepts inside `generate()`.
   They are latent terms in this data-generating model, not post-processing.
5. Map effects by IDs, add them to `log_mu`, sample NB2 counts, and return a
   copied DataFrame with `n_children_total`.
6. Never return random effects as columns.
7. Keep a deterministic `compute_log_mu()` method for formula tests.

**Validation gate**

Check finite positive means, nonnegative integer counts, coefficient scenarios,
NB2 mean/variance behavior, random-effect influence, no latent columns, and
reproducibility.

**Delete after gate**

- `stages/total_children.py`
- `TotalChildrenDesignBuilder`
- total-count-only functions in old `transforms.py`

### Step 8: Replace Cohort Stage

1. Add `CohortCompositionSimulator` to `outcomes.py`.
2. Build lifecycle features in a private method.
3. Generate the separate building cohort random effect inside this component.
4. Convert lifecycle scores to probabilities and sample multinomial counts.
5. Return a copied DataFrame with all three cohort columns.

**Validation gate**

Check finite nonnegative probabilities summing to one, integer cohort counts,
row-wise cohort-to-total identity, expected lifecycle direction, no latent
columns, and reproducibility.

**Delete after gate**

- `stages/cohort_composition.py`
- `CohortDesignBuilder`
- remaining obsolete `design.py` code

### Step 9: Add Explicit Building-Level Transformation

1. Implement `to_building_level()` in `pipeline.py` or as a small private
   pipeline helper.
2. Group apartment outcomes by `building_id`.
3. Merge targets into buildings with `validate="one_to_one"`.
4. Merge neighborhood context with `validate="many_to_one"`.
5. Enforce all accounting identities and one row per building.
6. Return a documented stable column order.

**Validation gate**

Compare every final target with a direct apartment groupby. Verify every
building appears exactly once and no merge relies on implicit keys.

**Delete after gate**

- `stages/aggregation.py`
- notebook manual `df_all` merge chain

### Step 10: Replace Pipeline Framework

1. Rewrite `StudentPopulationSimulator` as a short explicit sequence.
2. `run()` returns the final building DataFrame.
3. `run_details()` returns a small frozen `SimulationResult` with named
   intermediate DataFrames.
4. Do not retain dynamic registration, `run_until`, generic table dictionaries,
   metadata tracking, or schema dispatch.

**Validation gate**

Check full-run reproducibility, final contract, intermediate consistency, and
that the pipeline source reads as one short sequence.

**Delete after gate**

- `stages/base.py`
- `stages/__init__.py`
- remaining `stages/` directory
- `state.py`
- `metadata.py`
- `schemas.py`
- old registry/state pipeline code

### Step 11: Collapse Validation And Public API

1. Keep essential checks next to owning components and final aggregation.
2. Keep calibration and recovery in tests, not runtime report classes.
3. Narrow `__init__.py` to the config loader, five components, pipeline,
   `SimulationResult`, and genuinely reusable features.
4. Do not add compatibility adapters for removed classes.

**Validation gate**

Import the documented API, run component/calibration/recovery tests, and search
for references to removed symbols.

**Delete after gate**

- `validation/`
- obsolete `transforms.py` after `features.py` replacement
- tests for registry, state, schema registry, metadata, report classes, and old
  exports

### Step 12: Update Notebook And Documentation

1. Update the notebook to use:

   ```python
   final_df = StudentPopulationSimulator(config).run()
   ```

2. Use `run_details()` only for apartment-level EDA.
3. Use `to_cohort_long()` for cohort plots.
4. Remove manual and implicit `df_all` merges.
5. Update README and active docs around the five components.
6. Keep the mathematical model document as the formula authority.
7. Move superseded implementation documents to `docs/legacy/` or delete them
   after confirming no unique information remains.

**Validation gate**

Restart the notebook kernel and execute every cell in order. Verify final and
intermediate DataFrames, plots, reproducibility, and export behavior.

### Step 13: Final Cleanup Gate

1. Run the complete unit, calibration, and slow recovery suites.
2. Run compile and import checks.
3. Search for old stage/state/schema/metadata/design/validation symbols.
4. Confirm the package tree contains only compact modules.
5. Search docs and notebook for stale table names.
6. Remove temporary characterization hashes and migration helpers.

**Final package target**

```text
src/student_simulator/
    __init__.py
    config.py
    features.py
    neighborhood.py
    building.py
    apartment.py
    outcomes.py
    pipeline.py
```

## 6. Deletion Rule

Never delete a working implementation before its replacement passes the
focused validation gate. Once the gate passes, delete the old file in the same
migration step. Do not preserve it as an adapter, alternate path, or deprecated
alias unless a concrete external consumer is identified.

## 7. Completion Criteria

The migration is complete when:

- all component and full-pipeline tests pass;
- calibration and coefficient recovery remain acceptable;
- the notebook runs from a clean kernel;
- `run()` directly returns the enriched building-level DataFrame;
- no latent random effects are exported;
- no implicit merges remain;
- no old stage/state/schema/metadata/validation references remain; and
- the compact package tree is the only active implementation.

After these simulator criteria were satisfied, clean notebook execution became
an input contract for the marimo migration rather than a reason to retain
Jupyter. See [MARIMO_MIGRATION_PLAN.md](MARIMO_MIGRATION_PLAN.md) for the
current research-tooling completion criteria.
